# Security Policy

## Reporting a vulnerability

Email **security@veilmesh.com**. Please do not open a public issue for anything that
would let someone bypass verification.

Include what you need to make the problem reproducible: the version or commit, the
tier involved (CLI, Service Worker, extension), and a manifest, trust root or
statement that triggers it. Test key material is fine to attach — everything under
`testdata/` is public and test-only.

You should get an acknowledgement within three working days and an assessment within
ten. If a fix is warranted we will agree a disclosure date with you; the default is
publication once a release is out, and we will credit you unless you ask otherwise.

## What counts as a vulnerability

The protocol is specified in [`SPEC.md`](./SPEC.md) and the boundaries it does **not**
claim to defend are listed in §1 and in the threat model in [`README.md`](./README.md).
A report is in scope if it shows one of these:

- A manifest, rotation or revocation statement that a verifier accepts without a
  qualifying threshold of valid signatures (SPEC §8.1).
- Tampered bytes that Tier 1 serves to a page, or that `verify` / `audit` calls clean.
- The Rust and JavaScript verifiers reaching different verdicts on the same input.
  These are two implementations of one specification and any divergence is a bug —
  see SPEC §11 and `testdata/conformance_vectors.json`.
- Any path that reads private key material the operator did not intend to expose,
  or that signs with a key the trust root does not authorise.
- A way to suppress or replay a revocation such that a revoked key still counts
  (SPEC §9.2).

## What is already known, and is not a vulnerability

These are documented limits, not oversights. A report describing one of them will be
closed with a pointer here, though a report showing one is *worse* than documented is
very much wanted.

- **The first visit to a compromised origin.** Tier 1 is not installed yet. Only the
  Tier 2 extension covers it, and on Chrome it detects rather than blocks — Chrome's
  MV3 gives an extension no access to a response body.
- **Inline scripts in the initial HTML.** The Service Worker sees no `fetch` event for
  them. CSP hashes are the defence, generated by `sign --headers-out`.
- **A stolen threshold of signing keys.** Indistinguishable from a legitimate build,
  by construction. That is what `recovery` keys and rotation are for.
- **`source.slsa_provenance` is a claim by the signer**, not an attestation by a
  builder, and the same key signs both (SPEC §1, §6.3).
- **`audit --rekor-lookup` is a lookup.** It compares a hash against what the endpoint
  at `--rekor-url` reports. It does not verify the log's signed entry timestamp or an
  inclusion proof, and the flag is named accordingly.
- **The Guardian script in the browser extension runs in the page's own world.** It is
  telemetry and accident-protection; a hostile page can restore a clean `fetch` from a
  fresh realm in two lines. It is documented as such and is not a boundary.
- **Key files are unencrypted on disk** unless both halves are remote (SPEC §4.6). A
  `recovery` key stored next to the build keys defeats its own purpose; the tool says
  so at `keygen` time.

## Supported versions

Pre-1.0. Fixes land on `main` and in the next tagged release; there are no maintained
release branches yet. If that matters to your deployment, pin a tag and watch releases.

## Cryptography

Ed25519 (RFC 8032, strict verification) and ECDSA P-256, both required of every signer
— see SPEC §4.1 and §2.1 for the encodings, which are the most likely source of an
interop bug. If you find a case where `ed25519-dalek` and WebCrypto disagree, that is
squarely in scope.
